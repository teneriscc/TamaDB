Document-centric transmission cache — REST API reference.

TamaDB is a document-centric transmission cache for smart-endpoints / dumb-pipes architectures: a JSON document-oriented cache engine that validates, versions, and delivers producer data to consumers. This is the complete REST API reference for Increment 1.

This document is the single source of truth for the TamaDB HTTP surface. It is linted in CI (redocly lint) and rendered to the published API Reference by Redoc, so the docs cannot silently drift from the contract.

Conventions

  • All endpoints exchange application/json, except the ingestion endpoints, whose request body is the bare JSON document (see Ingestion).
  • Every endpoint lives under the /api/v1 prefix except GET /health.
  • There is no authentication in Increment 1.
  • Path parameters are shown as {paramName}.

Upsert semantics

TamaDB documents are upserted — there is no separate create vs update. The first ingest of a given identity creates the document (HTTP 201); a subsequent ingest of the same identity merges into it (HTTP 200), preserving absent leaves and incrementing the version number.

Document identity and identityKind

A document's identity (D-Id) is derived from one or more payload fields annotated with the identityKind keyword in the schema. Identity is scoped to (Document_Type, D-Id).

identityKind is a custom (vendor) JSON Schema keyword that TamaDB reads from registered schemas to extract the D-Id. It is attached to scalar leaf properties and takes one of two values:

  • primary-key — a field that contributes to the document's own identity.
  • parent-key — a field that contributes a parent/ancestor identity segment.

It may be annotated at any object-nesting depth (universal nested-path identity, since 0.2.0); the field is addressed by its root-to-leaf Identity_Path. Arrays are never traversed (atomic in Increment 1) and the annotated value must be a scalar. The keyword is ignored by schema validation (Ajv runs with strict: false) and consumed only by the D-Id Extractor. It is therefore a property of the posted schema, not a request/response field. See the Schemas tag for how to register a schema carrying identityKind.

A composed (multi-field) D-Id is expressed in a URL by joining its parts with the : delimiter. Each part is percent-encoded (via encodeURIComponent, and : is additionally encoded as %3A) so that a part value may itself contain the delimiter, /, or other reserved characters without corrupting the part boundaries. In response bodies, a single-key dId is a string and a composed dId is an array of strings.

TTL & expiry (sliding window)

A cached document's TTL is a sliding window anchored to its last update (lastUpdateTime + effectiveTTL), re-armed on every store (create or merge) — since 0.4.0. Reads and value-search listings never re-arm the window. A continuously-updated document therefore persists indefinitely by design (the producer owns the cache lifetime). A store targeting an expired-but-salvageable document revives it.

The TTL hierarchy is Document > Document_Type > Instance (most specific wins). TamaDB-Expire-At is an absolute, non-sliding, non-salvageable deadline that overrides TTL.

Document metadata and timestamps

Every store appends a timestamp entry to the stored document carrying a Request_Timestamp (t1, request receipt — the versioning / history / TTL-anchor time) and a Commit_Timestamp (t1+m, write-completion time). As of 0.4.1 the Commit_Timestamp is populated on every stored entry (it was previously always empty).

These timestamps are document metadata, not part of the default retrieval response: GET /api/v1/documents/{documentType}/{dId} returns the stored document's own fields (the producer payload plus any enrichment), and the mode / path options only select which data fields are returned — they never emit the metadata. The Commit_Timestamp is delivered on the metadata-delivery (webhook) payload, which the subscription → webhook pipeline carries; that payload is modelled when the delivery pipeline ships.

Error responses

All errors share a consistent shape (code + message, with optional reason, context, quarantineRef, warning). See the Error schema and the error-code → HTTP-status table in httpStatusForCode.

required

  • auto — the engine selects a strategy automatically.

The active log verbosity, most to least verbose:

  • info — informational events and above.
  • warn — warnings and errors only.
  • error — errors only.
  • silent — logging disabled.

Admin

Operational admin endpoints (e.g. graceful shutdown).

Trigger a graceful shutdown

Responds 200 immediately, then (asynchronously) drains in-memory documents to disk, persists all component state, closes the HTTP server, and exits the process. The recommended cross-platform way to stop TamaDB (SIGTERM can be unreliable on some platforms). After the response, the server stops accepting new requests.

Ingestion

Document ingestion. The request body is the bare JSON document; per-request instructions travel as reserved TamaDB-* Control_Headers.

Ingest a document (default channel)

Ingest a document for {documentType} via the default channel. The request body is the bare JSON document (a JSON object), not a wrapper. Per-request instructions are supplied as reserved TamaDB-* Control_Headers (see parameters).

Returns 201 when the document is created and 200 when an existing document is merged (upsert). On a payload-level rejection the response carries an Error with an optional quarantineRef.

Each successful store records a timestamp entry on the stored document with a populated Commit_Timestamp (write-completion time; see Document metadata and timestamps). This metadata is not returned in the ingest response — the response body is the IngestResult below.

Documents

Retrieve, delete, value-search, and set per-document TTL.

Retrieve a document (or glob-match)

Retrieve a single document by {documentType} and {dId}.

If {dId} contains glob characters (* or ?), the endpoint switches to glob retrieval and returns a { matches, count } collection instead of a single document.

A TTL-expired but salvageable document is served in place as a Best-Effort Read (visibility only — the read does not re-arm the TTL, restore the document, or clear its soft-delete state).

Value-based search within a Document_Type

Returns all documents of {documentType} whose field equals value.

includeExpired controls whether TTL-driven salvageable soft-deletes are surfaced. It defaults to true when omitted. Search is visibility-only: it never alters the TTL clock or persists a state change. A document listed by search is not guaranteed retrievable by a later point lookup (Req 15.9).

Request Body schema: application/json

required

The field name (or path) to match on.

required

The value to match (any JSON type).

includeExpired
boolean
Default: true

Whether TTL-driven, salvageable soft-deleted documents are surfaced in the results (visibility only — never alters the TTL clock or persists a state change):

  • true (default) — include salvageable TTL-expired documents, consistent with point-lookup Best-Effort Read.
  • false — return only live (non-expired) documents.

Get the active storage strategy

Responses

Response Schema: application/json
mode
required
string (StorageMode)
Enum: "auto" "memory" "disk" "hybrid"

The storage strategy governing where documents are held:

  • auto — the engine selects a strategy automatically.
  • memory — in-memory only (fastest; not durable across restart).
  • disk — persisted to disk (durable; nothing buffered in memory).
  • hybrid — in-memory working set with disk persistence.

/health reports the active mode; GET/PUT /api/v1/config/storage-strategy reads and changes it at runtime.

Get the quarantine policy

Responses

Response Schema: application/json
policy
required
string (QuarantinePolicyValue)
Enum: "off" "data-errors-only" "all-rejections"

Which rejected ingests are captured in quarantine:

  • off — nothing is quarantined.
  • data-errors-only — only producer-content (payload-stage) errors: a malformed body (PARSE_ERROR) or a schema/enrichment validation failure. Control-plane and routing/config rejections are excluded. (A rename to payload-errors-only is a deferred breaking change.)
  • all-rejections — every rejection, including routing/config errors.

Get enrichment policies

Responses

Response Schema: application/json
precedence
string
Enum: "environment-over-content" "content-over-environment"

Who wins when a channel enrichment binding and the producer payload both set the same field:

  • environment-over-content — the channel-configured (environment) value overrides the producer-supplied value.
  • content-over-environment — the producer-supplied value wins.
conflictResolution
string
Enum: "accept-and-warn" "discard-and-error"

What happens on an enrichment conflict:

  • accept-and-warn — apply the precedence rule, store the document, and emit a warning.
  • discard-and-error — reject the ingest with ENRICHMENT_CONFLICT (and quarantine per policy).

Response Schema: application/json
level
string (LogLevel)
Enum: "debug" "info" "warn" "error" "silent"

The active log verbosity, most to least verbose:

  • debug — everything (default).
  • info — informational events and above.
  • warn — warnings and errors only.
  • error — errors only.
  • silent — logging disabled.
destination
string (LogDestination)
Enum: "stdout" "file" "none"

Where log output is written:

  • stdout — standard output (default).
  • file — a file on disk (requires filePath).
  • none — discard log output.
